# **Expert Analysis of Firebase Hosting Header Proxies and Cloud Run Integration for Optimistic Concurrency**

## **Executive Summary**

The integration of Firebase Hosting as a reverse proxy and caching layer in front of Google Cloud Run provides a globally distributed, high-performance architecture for modern web applications. However, implementing optimistic concurrency controls—which rely on precise HTTP header semantics such as ETag, If-Match, and the 412 Precondition Failed status code—requires a rigorous understanding of the intervening proxies. When a client application attempts to mutate state on a backend via optimistic concurrency, any interference by a Content Delivery Network (CDN) or load balancer can result in fatal state mismatches, false preconditions, or the serving of stale entity tags.  
This exhaustive analysis evaluates how Firebase Hosting handles conditional-request headers and status codes when traffic is routed to a Cloud Run backend. Drawing strictly from current official Google Cloud and Firebase documentation, this report delineates explicit platform guarantees from inferred behaviors based on the underlying Google Cloud CDN and Global External Application Load Balancer architectures. The analysis directly addresses request header passthrough (If-Match), response header passthrough (ETag), HTTP status code un-cacheability (412 Precondition Failed), default caching interventions, and the profound architectural differences between traditional Firebase rewrites, the experimental Next.js web frameworks integration, and the modern Firebase App Hosting paradigm.

## **Architectural Context: Optimistic Concurrency and Intermediary Proxies**

Optimistic concurrency control in RESTful APIs operates on the assumption that multiple clients may attempt to read and write to the same resource simultaneously, but that conflicts are relatively rare. Rather than locking the database, the API relies on standard HTTP conditional requests to detect conflicts before committing a mutation.  
The state machine follows a strict sequence defined by HTTP RFC standards. First, the client issues a GET request to retrieve the resource state. The server responds with the resource payload and an ETag (Entity Tag) header, which acts as an opaque identifier representing the specific version of that resource. Second, when the client attempts to mutate the state via a PUT, POST, or PATCH request, it includes an If-Match request header containing the previously retrieved ETag value. Finally, the server evaluates the If-Match value against the current resource state in the database. If the tags match, the mutation proceeds, typically resulting in a 200 OK or 204 No Content response. If the tags do not match—indicating that another client has mutated the resource in the interim—the server rejects the request with a 412 Precondition Failed status code.  
For this mechanism to function securely and reliably, any reverse proxy situated between the client and the origin server must preserve the integrity of both the ETag and If-Match headers. It must also accurately relay the 412 status code without erroneously intercepting it or returning a cached response. The introduction of Firebase Hosting and Cloud CDN into this request path introduces variables regarding header modification, cookie stripping, and dynamic payload compression that must be carefully navigated.

## **Request Header Passthrough: The Handling of the If-Match Header**

The primary concern for optimistic concurrency on the inbound request path is whether Firebase Hosting passes the If-Match header to the Cloud Run backend unmodified, or if the proxy strips, renames, or alters it.

### **Distinguishing Explicit Documentation from Architectural Inference**

It is critical to state plainly that the official Firebase Hosting documentation does not explicitly name the If-Match header in its proxying or routing rules. There is no single sentence in the Firebase literature that explicitly guarantees the unmodified passthrough of conditional-request headers. Therefore, any conclusion regarding the If-Match header must be derived as a high-confidence inference based on the documented behavior of Firebase's proxy mechanics and the underlying Google Cloud load balancing infrastructure.

### **Stripping and Modification Mechanics**

When Firebase Hosting rewrites traffic to a Cloud Run container, the inbound request passes through Google's Global External Application Load Balancer and Cloud CDN. The official documentation for Google Cloud Load Balancing (https://docs.cloud.google.com/load-balancing/docs/https/custom-headers-global)1 and Firebase Cache Management (https://firebase.google.com/docs/hosting/manage-cache)2 explicitly details the headers and payload elements that are modified or stripped by the proxy layer.  
The proxy architecture aggressively sanitizes incoming requests to optimize CDN cache keys and protect backend infrastructure. This sanitization occurs in several distinct categories.

| Modification Target | Documented Behavior | Architectural Rationale |
| :---- | :---- | :---- |
| **Cookies** | Firebase Hosting explicitly strips cookies from incoming requests routed to Cloud Run or Cloud Functions2. The only exception is the specially named \_\_session cookie, which is permitted to pass through to the backend execution2. | Stripping arbitrary cookies is necessary to allow for efficient CDN cache behavior. If all cookies were passed, every request would yield a unique cache key, rendering the CDN useless. |
| **Hop-by-Hop Headers** | Google Cloud Load Balancers explicitly strip hop-by-hop headers, including Keep-Alive, Transfer-Encoding, TE, Connection, Trailer, and Upgrade1. | These headers are intended for a single transport-level connection. Propagating them through a proxy layer violates RFC 2616 and disrupts connection pooling between the load balancer and the backend. |
| **Reserved Google Headers** | Any request header beginning with X-Google, X-Goog-, X-GFE, or X-Amz- is stripped or overwritten1. Furthermore, the X-User-IP and CDN-Loop headers cannot be modified or reliably passed as custom headers1. | These namespaces are strictly reserved for Google's internal routing telemetry, security policies, and edge-to-origin communication. |
| **Host Header** | The Host header is heavily regulated and cannot be appended or removed via custom header rules at the proxy layer1. | The Host header is critical for Virtual IP routing and Server Name Indication (SNI) resolution across the global edge network. |

Because the If-Match header is a standard, end-to-end HTTP request header used for entity validation, and because it does not appear on the explicitly documented list of stripped hop-by-hop or reserved headers, the architectural inference is that it passes through to the backend service unmodified during a cache miss or a bypassed request. Furthermore, Google Cloud CDN documentation explicitly states that the CDN can utilize conditional requests for validation (https://docs.cloud.google.com/cdn/docs/caching)3, which confirms that the underlying infrastructure understands and respects standard conditional semantics.  
State-mutating HTTP methods—such as PUT, POST, and PATCH—are never cached by Cloud CDN. The documentation explicitly states that only GET and HEAD requests are eligible for caching (https://firebase.google.com/docs/hosting/manage-cache)2. Therefore, when a client issues a PUT request with an If-Match header to mutate data, the request bypasses the CDN entirely and is routed directly to the Cloud Run backend, ensuring the If-Match header arrives unmodified.

## **Response Header Passthrough: The Handling of the ETag Header**

The transmission of response headers from the Cloud Run backend back to the client dictates whether the client receives the correct entity tag required for subsequent optimistic concurrency validations. The user query specifically asks whether custom or standard ETag response headers are preserved by Firebase Hosting.

### **ETag Preservation and the Dynamic Compression Paradox**

The official Google Cloud CDN documentation explicitly confirms that the CDN relies on ETag headers generated by backend instances to confirm the freshness of cached objects (https://docs.cloud.google.com/cdn/docs/troubleshooting-steps)4. Because the infrastructure natively utilizes ETags for internal cache revalidation, it inherently preserves them and passes them downstream to the client. If backend instances serve different ETags for the same object, Cloud CDN interprets this as a cache miss and refreshes the object4.  
However, the preservation of the ETag header is subject to a severe architectural caveat that can entirely disrupt optimistic concurrency implementations. This caveat is the proxy's **Dynamic Compression** feature.  
If dynamic compression is enabled at the load balancer or CDN layer, the infrastructure intercepts compressible content types (such as application/json or text/html) returned by the Cloud Run origin. When the proxy compresses the response payload—typically using Brotli or Gzip—the payload is fundamentally altered from the byte-for-byte representation generated by the origin. According to the Google Cloud CDN dynamic compression documentation (https://docs.cloud.google.com/cdn/docs/dynamic-compression)5, when a response is compressed at the edge, the proxy aggressively modifies the ETag header.  
The documentation explicitly states: *"Any strong entity tag is replaced with a weakened version, indicated by the prefix W/"*5.  
This protocol behavior introduces a critical hazard for optimistic concurrency APIs. A typical failure sequence unfolds as follows:  
First, the Cloud Run backend computes a strong ETag based on the uncompressed JSON payload (e.g., ETag: "v1.2.3") and returns the response. Second, the Cloud CDN edge node intercepts the response, compresses the payload with Brotli, and dutifully downgrades the entity tag to a weak tag (e.g., ETag: W/"v1.2.3") before sending it to the client. Third, the client stores the weak ETag and subsequently attempts a state mutation using the If-Match header (e.g., If-Match: W/"v1.2.3").  
According to HTTP RFC 7232 semantics, the If-Match header explicitly requires strong validation. Many strict backend routing frameworks will automatically reject an If-Match header containing a weak ETag prefix, resulting in an immediate 412 Precondition Failed error, even though the underlying database record has not actually been mutated by another client.  
Therefore, while the documentation explicitly confirms that the ETag response header is passed through, developers must account for proxy-level mutation. If Cloud CDN dynamically compresses the payload, it will explicitly alter a strong ETag into a weak ETag. To mitigate this, API backends running on Cloud Run must either be explicitly programmed to handle weak ETags in If-Match headers, or the backend must handle compression natively (serving the compressed payload with its own strong ETag), thereby preventing the CDN from applying secondary compression and modifying the header.

## **HTTP Status Code Passthrough: The 412 Precondition Failed Status**

Optimistic concurrency relies entirely on the server's ability to signal a state mismatch by returning a 412 Precondition Failed HTTP status code. The analytical question is whether Firebase Hosting passes this non-2xx status code through unmodified, or whether the caching layer intercepts or alters it.  
The Firebase and Cloud CDN documentation does not explicitly detail the handling of the 412 Precondition Failed status code in a dedicated section. To establish the proxy behavior, one must analyze how the documentation defines the boundaries of cacheable status codes.  
According to the Firebase App Hosting cache optimization documentation (https://firebase.google.com/docs/app-hosting/optimize-cache)6, Cloud CDN will store responses in the cache only if specific conditions are met. The documentation provides a strict, exhaustive list of status codes that are eligible for caching. This list includes standard success codes (200, 203, 204, 206, 300, 301, 302, 307, 308\) and specific error codes (404, 405, 410, 421, 451, 501\)6.  
The documentation explicitly notes how certain errors are handled. For example, if a Cloud Run backend returns a 404 Not Found error, the CDN caches this response for a default of 10 minutes unless the backend overrides this duration with custom Cache-Control headers (https://firebase.google.com/docs/hosting/manage-cache)2. This behavior ensures that traffic spikes targeting non-existent URLs do not overwhelm the origin compute resources.  
Crucially, the 412 Precondition Failed status code is absent from the exhaustive list of cacheable status codes6. Because it is not a cacheable success code, and because it is not explicitly targeted for edge-level caching like a 404, the architectural inference is that the 412 status code is treated as dynamic, uncacheable traffic. It is passed through unmodified to the client. The caching layer will not intercept, alter, or synthesize a 412 status code, nor will it serve a cached version of a previous 412 response on subsequent requests. The client is guaranteed to receive the authoritative precondition failure directly from the Cloud Run origin.

## **Default Caching Behaviors for Rewritten Requests**

A major architectural concern in proxy-based deployments is that a CDN might cache a successful GET request, subsequently serving a stale resource and a stale ETag to the client. If the client attempts to mutate the state using a stale ETag, the request will correctly—but frustratingly—fail with a 412 Precondition Failed because the client was operating on outdated information.  
The user query specifically asks whether Firebase Hosting applies any default caching behavior to rewritten requests that could interfere with conditional requests. The explicit documentation reveals that Firebase Hosting applies highly favorable defaults for optimistic concurrency architectures by inherently protecting dynamic content.

### **The Default Cache-Control: private Directive**

According to the Firebase Hosting Cache Management documentation (https://firebase.google.com/docs/hosting/manage-cache)2, Firebase Hosting automatically caches requested static content on its global CDN. However, because backend code from Cloud Functions and Cloud Run generates content dynamically, requests handled by these backend rewrites do not cache on the CDN by default2.  
The documentation explicitly states that Firebase Hosting achieves this by injecting a Cache-Control: private header for dynamic content2. The private directive is an explicit instruction that prohibits intermediate shared caches—such as the Firebase CDN—from storing the response. It ensures that every inbound GET request routed to Cloud Run actually reaches the Cloud Run instance. It permits only the local browser of the requesting user to cache the content2.  
This default behavior is the ultimate safeguard for optimistic concurrency. Because the CDN does not cache the API response by default, the client is guaranteed to receive the most current resource state and the most current ETag directly from the database, eliminating proxy-induced stale tag collisions.

### **The Impact of Explicit Overrides and Vary Header Automation**

Developers can explicitly override this default behavior to reduce Cloud Run execution costs by returning a custom Cache-Control header from their application, such as Cache-Control: public, max-age=300, s-maxage=6002. The s-maxage directive specifically instructs the CDN to cache the dynamic response.  
If a developer implements this override on an optimistic concurrency API, the CDN will cache the API response and its associated ETag. If a resource is subsequently mutated by User A, and User B then requests the resource within the s-maxage window, User B will receive the cached payload and a stale ETag from the CDN edge. User B's subsequent mutation attempt will correctly fail with a 412 Precondition Failed. This is not a failure of the Firebase proxy; it is the correct semantic enforcement of optimistic concurrency combined with developer-mandated explicit caching.  
To mitigate cross-user data leakage when developers do enable public caching, Firebase Hosting automatically intervenes in the Vary header. The Vary header dictates which request headers must match for a cached response to be considered valid for a subsequent request. The documentation explicitly states that Firebase Hosting automatically appends Cookie and Authorization to the Vary header (e.g., resulting in a compilation like vary: x-fh-requested-host, accept-encoding, cookie, authorization) (https://firebase.google.com/docs/hosting/manage-cache)2. This automated security feature ensures that if a response is cached, it is uniquely keyed to the user's specific session or authorization token, preventing the accidental leakage of state across different users and significantly reducing the likelihood of cross-user ETag collisions.  
It is critical to note that Firebase Hosting does not provide a mechanism to programmatically purge or invalidate individual dynamic cache keys upon a resource mutation. If Cache-Control: public is utilized on a state-retrieving API endpoint, the application architecture must be resilient enough to tolerate serving stale ETags until the defined s-maxage expires naturally.

## **Deployment Paradigms: Plain Rewrites vs. Web Frameworks vs. App Hosting**

The user query highlights a highly nuanced distinction in Firebase architecture: the difference in passthrough behavior between the Firebase "web frameworks" integration (specifically the Next.js integration utilizing firebase deploy with framework detection) versus a plain custom rewrite rule pointing at an existing Cloud Run service.  
This distinction is profound. The evolution of Firebase's product offerings has resulted in three entirely different backend topologies, each governing how headers are processed and where compute is executed.

| Deployment Methodology | Infrastructure Provisioning | Header Processing Mechanism | Proxy and CDN Layer |
| :---- | :---- | :---- | :---- |
| **Traditional Rewrites (firebase.json)** | Developer manually deploys to an existing Cloud Run service7. | Headers processed strictly according to firebase.json configuration blocks. | Classic Firebase Hosting CDN and routing logic. |
| **Web Frameworks CLI (Next.js via firebase deploy)** | CLI auto-provisions **Cloud Functions for Firebase**8. | CLI attempts to translate next.config.js headers to Firebase equivalents. Unsupported rules trigger function fallbacks8. | Classic Firebase Hosting CDN. |
| **Firebase App Hosting (Modern Standard)** | Platform natively deploys Next.js to **Cloud Run** via Cloud Build6. | Controlled natively by the framework. Extremely strict validation of Vary headers by the CDN9. | Google Cloud CDN with specialized App Hosting edge configurations6. |

### **The Architecture of Traditional Custom Rewrites**

When a developer manages their own Next.js or API deployment as a Docker container to a pre-existing Cloud Run service, they configure a standard rewrite in the firebase.json file (https://firebase.google.com/docs/hosting/full-config)7.  
In this topology, Firebase Hosting acts as a traditional, configurable proxy. The incoming request strikes the Firebase CDN, evaluates the Cache-Control header, and proxies the payload to the specified Cloud Run service ID2. The request paths and query strings are passed entirely intact. Custom headers defined in the "headers" block of firebase.json are appended to the response7. Because the backend compute is a dedicated Cloud Run container managed by the developer, concurrency and scaling behave predictably. Conditional request headers like If-Match flow through the proxy subject only to the standard cookie-stripping and hop-by-hop sanitization described earlier2.

### **The Architecture of the Web Frameworks CLI Integration**

If a developer relies on the experimental firebase deploy web framework detection for Next.js, the Firebase CLI intercepts the deployment and fundamentally alters the infrastructure compute layer.  
The documentation explicitly states that if the CLI detects dynamic server-side logic in the Next.js application—specifically the usage of getServerSideProps—it deploys that logic to **Cloud Functions for Firebase**, not Cloud Run (https://firebase.google.com/docs/hosting/frameworks/nextjs)8.  
This shift to Cloud Functions carries significant implications for header management. During deployment, the Firebase CLI attempts to respect the redirects, rewrites, and headers declared in the application's next.config.js file by converting them into equivalent Firebase Hosting configurations8. However, the documentation explicitly notes a fallback behavior: if a specific Next.js header, redirect, or rewrite cannot be successfully converted to a native Firebase Hosting rule, the CLI abandons the static configuration and automatically builds a Cloud Function to handle the traffic—even if the application is not actively utilizing Server-Side Rendering (SSR) or image optimization8.  
While the header passthrough logic remains governed by Firebase Hosting's classic proxy rules, the shift from a highly concurrent Cloud Run container to event-driven Cloud Functions introduces cold starts and different concurrency models that can impact the latency of optimistic concurrency validations. Furthermore, the usage of Next.js Image Optimization is heavily restricted in this environment, as it triggers the creation of additional Cloud Functions that do not interoperate well with Firebase Hosting preview channels8.

### **The Architecture of Firebase App Hosting**

Because of the complexity and limitations of the experimental Web Frameworks CLI, the official documentation strongly recommends that developers "graduate" to the newer **Firebase App Hosting** product (https://firebase.google.com/docs/app-hosting)6. Firebase App Hosting supersedes the older CLI integration and provides a fundamentally different deployment and proxy architecture that natively supports Cloud Run.  
Firebase App Hosting utilizes a GitHub integration and Google Cloud Buildpacks to automatically detect Next.js, construct a container, and deploy it to a dedicated Cloud Run service without requiring manual configuration6.  
Crucially, App Hosting utilizes a dedicated Google Cloud CDN integration with far stricter caching rules than classic Firebase Hosting. The documentation for App Hosting troubleshooting (https://firebase.google.com/docs/app-hosting/troubleshooting)9 explicitly dictates severe limitations on the Vary header. The App Hosting CDN is restricted to using a specific, predetermined set of request headers in its cache keys. This whitelist includes Next.js-specific headers (e.g., RSC, Next-Router-State-Tree) and standard routing headers (e.g., Accept, Origin)6.  
The documentation establishes a strict cache-refusal policy: If a Cloud Run response in App Hosting contains a Vary header with a value that is *not* present in the allowed whitelist, **the CDN will completely fail to cache the response**6.  
For optimistic concurrency, the App Hosting architecture provides the most deterministic environment. By default, uncached requests are routed directly to the Cloud Run service6. Because If-Match validation relies on direct backend communication, the CDN's refusal to cache responses with non-standard Vary headers acts as a rigid fail-safe. It ensures that complex, dynamic API responses generated by Cloud Run are not erroneously cached at the edge, guaranteeing that clients receive authoritative ETags for subsequent state mutations.

## **Observability and Troubleshooting for Conditional Requests**

When diagnosing ETag mismatches, 412 errors, or suspected proxy interference, developers must rely on precise telemetry. Firebase Hosting provides integration with Google Cloud Logging to expose the exact proxy behavior (https://firebase.google.com/docs/hosting/web-request-logs-and-metrics)12.  
By linking a Firebase project to Cloud Logging, developers can view the granular details of every request processed by the CDN. The logs capture critical headers and routing data, including:

* status: The exact HTTP response status (e.g., 200 or 412), verifying whether the precondition failure was triggered.  
* cacheHit: A boolean field explicitly indicating whether the resource was served quickly from Hosting's CDN cache, or if it bypassed the proxy and made the full trip to the Cloud Run backend12.

By analyzing the cacheHit metric alongside the status metric, engineers can definitively prove whether a client received a stale ETag due to an aggressive caching rule (a cacheHit: true preceding a 412 error), or if the 412 error was generated by a legitimate concurrency conflict at the Cloud Run origin (cacheHit: false).

## **Strategic Synthesis and Final Conclusions**

For engineering teams implementing optimistic concurrency via conditional HTTP headers on a Next.js application deployed to Cloud Run behind Firebase Hosting, the official documentation yields the following architectural truths:  
First, **Header Integrity is Maintained (with severe caveats regarding compression).** Standard request headers like If-Match are passed to the backend unmolested when a cache miss occurs. Response headers like ETag are returned to the client. However, developers must be acutely aware of **dynamic compression**. If the proxy layer compresses the API response, it will convert a strong ETag into a weak ETag (W/), which will cause strict backend If-Match validation logic to fail abruptly5.  
Second, **Status Codes are Transparent.** A 412 Precondition Failed status code is treated as an uncacheable error and will be passed through to the client unmodified6. The CDN does not synthesize or cache these precondition failures.  
Third, **Defaults Protect Concurrency.** Firebase Hosting's default behavior of setting Cache-Control: private for all Cloud Run rewrites serves as a natural defense against stale ETag caching2. As long as developers do not explicitly override this with public max-age directives on their API endpoints, the CDN will not interfere with optimistic concurrency validations.  
Finally, **Deployment Methodology Dictates Infrastructure.** Using the experimental firebase deploy web framework integration quietly shifts dynamic compute away from Cloud Run and into Cloud Functions8. To utilize true Cloud Run architecture, developers must either rely on traditional firebase.json rewrites7 or migrate entirely to the modern **Firebase App Hosting** service, which offers native Cloud Run provisioning and highly strict Cloud CDN cache-key validation6.  
To ensure flawless operation of optimistic concurrency, system architects must disable dynamic compression for ETag-validated API routes or configure backend logic to safely parse and validate weak ETags. Furthermore, maintaining the default Cache-Control: private directive on all state-mutating and state-retrieving API endpoints is paramount to preventing the CDN from serving stale concurrency tokens.
